## Gap between the author's absolute numbers and ours

- verdict: **hardware** — Reported 0.761→0.550 ms, ours 1.255→0.951 ms (b2048 v32k); all five reported rows are 1.65-2.0× slower here, ratio-of-ratios 0.94-0.95 → **reproduced**. The Triton kernel at b2048 reads the whole logits matrix per search iteration, i.e. bandwidth-bound; 896 GB/s vs ~3.35 TB/s predicts ≈3.7×, the observed 1.65-2× says the kernel is not saturating either card, but the direction and size are hardware. Args match the author exactly (`--batch-sizes 128 2048 --vocab-sizes 32768 131072 --warmup-iters 5 --benchmark-iters 20`). The b128 rows have 10-30 % sd (0.0098/0.1018, 0.025/0.083): 5 warmup iters × ~0.1 ms is far too little for a P8-idling card to boost — see recommendation 6. Cannot be made 1:1; the ratio is the comparable quantity.

## Measurement policy (as pipeline/run_one.sh implements it)

- repeats: 5 per arm; ABBA across arms per repeat (A,B,B,A,A,B,...); one run = one `docker run` of the workload cmd per arm per repeat (same image, arm tree swapped in by the prelude)
- GPU pin `--gpus device=0`, env ['CUDA_DEVICE_ORDER=PCI_BUS_ID', 'CUDA_VISIBLE_DEVICES=0', 'HF_HUB_DISABLE_PROGRESS_BARS=1'], `--shm-size=2g`, per-run cap `WL_TIMEOUT=20m`
- GPU warm-up 2.0 s in the prelude; contention gate: wait while another tenant uses the GPU (>5 % util or a foreign compute process >1 GiB) or the CPU (load1 > nproc/2) (max wait 600 s, then run anyway, flagged in data/pr_<n>/work/contended_<arm>_<i>.txt)
- arm isolation `tree`: wipe the wheel's vllm/*.py, copy the arm's vllm/ over site-packages (compiled .so stay); machine.py snapshot per workload run -> data/pr_<n>/work/machine_<arm>_<i>.json
- noise model: measure.py: paired log-speedup, MAD sigma, theta = clip(k*sigma, theta_min, theta_max) with k/theta from config.yaml:measure
