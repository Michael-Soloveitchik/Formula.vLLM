▾Background: why reported ≠ reproducedclick to open

Two sets of numbers per PR. Reported = what the PR author measured on their machine. Reproduced = the same workload run here, baseline tree vs the PR's solution tree, same docker image, swapped .py trees only.

Absolute times are not comparable; ratios are. Authors ran H100-class nodes. This box:

GPURTX 5070 Ti 16 GB (sm_120), also driving the desktophostWSL2 on a hybrid i7-14700KFbandwidth896 GB/s vs 3.35 TB/s on H100launch floor~70–100 µs per sync, 3–10× the datacentre floor

So bandwidth-bound kernels run ~1.5–4× slower here, and anything under ~100 µs per call sits on the host launch/sync floor — those rows are flagged below_host_floor and their ratio is unreliable.

What we do to be fair. One GPU pinned, 2 s warm-up out of idle clocks, baseline / PR's solution runs interleaved A·B·B·A so drift hits both arms, a contention gate that waits for other tenants (and flags the run if it can't), a machine snapshot stored with every run, and a 20 min cap per run.

When the author gave only a % or a diff, it is applied to our reproduced baseline (marked * / +) so both columns live in the same unit.
